## 研究问题

推理系统优化只给 agent 一个最终吞吐或精度分数时，它很难判断问题来自算子、通信、内存还是调度。怎样把失败或退化变成能定位原因、指导下一次实验的反馈？

这是一篇 2026-09-17 发布的工程博客。GLM-5.3 驱动 Infra Agent，参与 GLM-5.3-Flash 的推理基础设施建设。标题中的 RSI（Recursive Self-Improvement，递归自我改进）是研究方向；作者明确承认尚未实现完整 RSI。

阅读依据：[原文](https://z.ai/blog/glm-built-its-inference-infrastructure)及其链接的 [FLA PR #1180](https://github.com/fla-org/flash-linear-attention/pull/1180)。以下区分作者报告、公开代码证据和本次讨论的判断。

## 核心方法

- **人定义目标、约束和验收标准。** 工程师搭建反馈环境，并审查数值语义、并发与架构等关键修改。
- **Agent 提假设、改代码、设计和执行实验。** 它可以主动定位缺陷，无须人预先指出具体 bug；但总体目标和反馈环境仍由人组织。
- **实验环境提供 dense feedback。** 这里指反馈足够具体、取得及时且成本低，并能由参考实现或对照实验验证。数值测试回答算得对不对，执行时间线解释时间花在哪里，性能实验检验某项修改在哪些条件下有效。
- **局部测试与端到端验收配合。** 能用单算子测试回答的问题先局部验证；候选修改仍需回到真实负载，确认整体收益和回归情况。某个 kernel 更快，可能因占用更多资源而妨碍通信重叠。
- **积累带适用条件的优化经验。** Agent 从已有实现中提取 optimization skeletons，即记录适用条件、变换方法、资源限制和验证证据的优化模板；新实验结果再补入经验库。

流程可概括为：人设定目标与范围 → agent 提出假设 → 修改与对照实验 → 局部反馈 → 修正假设 → 端到端验收 → 保存有效改动及适用条件。

## 关键发现

- **总体结果是作者报告。** 团队称不到两周完成从初始适配到生产准备，端到端吞吐相对初始基线约提升 3 倍。这包含工程师、agent 和多项系统优化的共同贡献，不能全部归因于 agent 或 dense feedback。
- **正确性案例有公开补丁。** Context Parallelism 路径的状态合并会累积数值误差。已合并的 [PR #1180](https://github.com/fla-org/flash-linear-attention/pull/1180) 增加可选的 `tf32x3` 精度路径及多卡测试；这是正确性修复，并非独立的吞吐提升证据，也不能仅凭 PR 证明 agent 的完整工作过程。
- **并发案例体现跨层定位。** 作者比较 Prefill 与 Prefill + KV Transfer，发现后者在部分场景损失超过 20%；时间线把问题指向未释放 Python GIL 的 C++ 调用。修复后，同条件性能差距降至 1% 以下。底层支持异步，不保证上层能及时提交任务。
- **Kernel 案例体现受控取舍。** Agent 发现沿 V 维切块导致归一化和门控重复计算，合并相关块并复用中间结果；作者报告该步相对前一版本加速 1.71 倍。这是局部收益，不能直接等同于服务整体加速。

## 我的提问

### Q1：所以这是 human-in-the-loop 的全栈优化，而不是 agent 自主优化自己的 harness？

这是本次讨论最终确认的主要区别。Harness 指围绕 agent 的工具、实验流程、反馈、记忆与执行控制。本文提供了一套供 agent 使用的优化 harness，但没有展示它自主改进这套 harness，并提高下一轮优化能力的完整证据。

| 比较项 | 本文实际展示 | Harness 自我改进需要展示 |
| --- | --- | --- |
| 优化对象 | 推理代码、kernel、通信与调度 | Agent 自己的工具、反馈、实验流程、记忆和策略 |
| 环境与标准 | 人组织环境和标准，agent 在其中构造实验 | Agent 发现环境不足并主动扩展它，最终验收仍有独立标准 |
| 直接结果 | 目标推理系统更快或更正确 | 后续任务中，agent 更能找到问题并高效验证方案 |
| 证据 | 正确性测试和端到端收益 | 独立任务、相同预算下，改进后的 harness 持续优于原版本 |

### Q2：Agent 没有主动设计环境和找缺陷吗？

不能一概否定。它确实会主动发现推理系统中的缺陷、构造最小复现和对照实验，并选择需要的观测方式。关键是区分：发现被优化系统的 bug，与发现自身工具或反馈机制的短板，是不同的改进对象。

文章把搭建可用反馈环境列为工程师职责；没有证明 agent 能自主判断整个环境缺了什么、重构环境，并使这种改变在后续独立任务中持续有效。

### Q3：不断更新 optimization skeleton library，算不算自我改进？

它是最接近该方向的部分：已验证经验能够影响下一轮优化。但文章没有给出经验库版本之间的对照，也没有分离经验积累对新任务效率和成功率的贡献。因此可以称为经验积累或初步线索，尚不足以证明 harness 的递归改进。

### Q4：没有更新模型权重，是否就不能叫自我改进？

不是。讨论初期强调未展示权重训练，后续进一步纠正：是否改权重并非关键判据。即使权重固定，agent 也可能通过改进自己的工具、反馈和实验策略，提高系统层面的能力。

需要证明的是：这一轮不只优化了目标系统，还提高了做优化的系统在下一轮的能力。人仍参与目标设定，也不自动排除这种系统层面的改进。本文缺少的主要是后续能力提升的独立证据。

### Q5：哪些内容值得借鉴到 video generation？

以下是本次讨论的建议，不是 Z.ai 已验证的视频实验。[Sol-Engine 公开论文](https://arxiv.org/html/2606.23743v1) 已包含加速方法的局部搜索、整体组合优化和人工质量验证；可以进一步补充错误定位及经验复用。

- **固定输入的局部检查。** 对同一个去噪 latent $x_t$，比较参考实现与候选实现的 attention、block 输出和噪声／速度预测，定位误差最先出现在哪一步、哪一层。
- **完整采样检查。** 让候选实现跑自己的生成轨迹，检查局部差异是否积累成闪烁、身份漂移、运动变形或音画不同步。局部误差小不保证长视频质量稳定；轨迹不同也不自动代表感知质量变差。
- **分阶段性能诊断。** 分别测 DiT、通信、VAE decode、视频编码和音频合成，并观察等待与重叠。验收同时看质量、完整请求延迟和固定 GPU 预算下的吞吐。
- **经验记录适用条件与失败案例。** 绑定模型版本、硬件、分辨率、视频长度、步数和精度，避免把短视频上的有效方案直接推广到长视频。

对于保持计算语义的 kernel 改写，参考实现可用于数值检查；对于量化、稀疏 attention、cache 或少步采样，还需要独立 prompts、多 seed 和人工盲评，不能让一个最终分数替代定位与验收。

以 [Sol-H3-Spark 公开时间分解](https://nvlabs.github.io/Sana/Sol-Engine/Sol-H3-Spark/) 为例，页面中 LTX refinement 占约 44%。若仅把该阶段加速两倍，并假设其他部分耗时不变，总体加速只能估算为：

$$
S_{\mathrm{total}}=\frac{1}{(1-f)+f/s}=\frac{1}{0.56+0.44/2}\approx 1.28.
$$

$f$ 是该阶段原始耗时占比，$s$ 是其加速倍数。这是依据公开时间分解的估算，不是新增实测结果；它说明应由端到端收益决定是否保留修改。

### Q6：怎样验证我们做的是 harness 改进，而不只是又一次工程优化？

可以在相同模型、任务和预算下，比较只提供最终指标、增加局部诊断、再增加已验证经验库的三种设置。观察相同 GPU 小时内，找到多少通过质量检查且降低端到端成本的方案。

若进一步主张 agent 自主改进 harness，需要记录它发现的环境缺陷、对工具或流程的实际修改，并冻结不同版本，在未参与改进的新任务上比较成功率、时间和成本。不能只在已反复尝试的任务上宣布能力提高，也不能让 agent 通过放宽验收标准得到更好成绩。

## 局限与疑问

- 文章是工程案例报告，没有给出足够对照来分离人、agent、反馈环境和各项优化的贡献。
- 未提供完整 agent 轨迹、可直接复现的 harness 配置或经验库版本对照；这些材料待补充。
- 已合并的补丁支持技术修改存在，不足以验证宣传中的全部自主性和总体效益。
- 没有展示多轮后继模型能力提升，也没有证明经验库积累能提升独立新任务上的优化能力。
- 视频生成缺少单一、可靠的质量判定器；自动指标可能遗漏运动和一致性退化，局部误差也不能直接替代感知质量。

## 我的判断

保留用户的判断：这是人设定范围、目标和反馈环境，agent 自主设计实验并优化目标系统的 human-in-the-loop 方案。不能据此断言它已实现自主优化自身 harness 的递归过程。

同时保留后续澄清：agent 并非只执行预先写好的实验，它可以主动查错和构造验证；改不改模型权重，也不是区分自我改进的关键。

Agent 的建议：对视频生成，优先把质量退化变成可定位、可复现、可修正的反馈，再验证这些反馈和经验是否提高后续优化效率。这比单独展示 agent 修改了多少代码，更能说明 harness 改进的价值。

## 下次只看这些

1. 人设目标和反馈环境；agent 自主提假设、查错、改代码和跑实验。Dense feedback 的重点是能定位、取得快、可验证。
2. 优化推理系统与改进优化者的 harness 是两层问题；经验库更新是线索，独立新任务上的后续能力提升才是关键证据。
3. Video gen 可先做同一 $x_t$ 的按层／按步比较，加完整生成质量检查；最终用相同预算、新任务和端到端收益验证价值。
