## 研究问题

稀疏 attention 已经跳过许多不需要的块，但被选中的块仍可能没有填满。KPage 解决的是这些块内部的无效占位，而不是继续删掉 attention 权重小的真实 token。

必须区分两件事：**只选择 10% 的块**，与**选中的块只有 10% 的位置有效**。前者是稀疏选择，后者才涉及本文的空位计算。选中一个块后，全部真实 token 仍然计算。

阅读依据为 [KPage v1 原文](https://arxiv.org/html/2610.28096v1)，提交于 2026-10-20。本文的主要优化发生在稀疏 attention kernel 内，稀疏选择规则保持不变。

## 核心方法

### 1. 以前怎么算，改完怎么算，为什么有效？

用一个简化例子说明：同一组 128 个 Q token 需要关注 A、B 两个 K/V 块。每块占 128 个位置，但各自只有 64 个真实 token，其余是 padding。

| 执行方式 | K/V 放入计算块的方式 | 名义 Q–K 计算位置 |
| --- | --- | --- |
| 固定 128 宽计算块，分别执行 A、B | A 的 64 个真实位置加 64 个空位；B 同样 | 两个 $128\times128$ tile |
| KPage 跨块拼接 | A 的 64 个真实 token 与 B 的 64 个真实 token 拼在一起 | 一个 $128\times128$ tile |

矩阵乘法按整块执行，给 padding 加 mask 可以保证它不影响结果，却不意味着硬件自动省掉对应位置的乘加。KPage 将相同的有效交互放进更少的计算块，同时保留适合 Tensor Core 的大块形状。这个例子只说明计算位置如何减少，忽略了末尾对齐和加载开销，不能直接当作两倍实测加速。

### 2. 以 16 行为一页，在加载时直接拼好

对有效行数为 $c_b$ 的逻辑 K/V 块，所需页数为：

$$
p_b=\left\lceil\frac{c_b}{16}\right\rceil.
$$

拼接前，每块占 128 行；页表示只需 $16p_b$ 行，因此每块页内残余 padding 至多 15 行，最后还可能有计算流水线要求的对齐空位。

对一个 Q 块，KPage 仅取它原来选中的 K/V 块里的有效页，先排列完整页，再处理残缺尾页。加载端按页表从原始 K/V 直接收集到 shared memory，不先在 HBM 中生成一份重排后的 K/V。随后 QK、online softmax 和 PV 继续使用规则的大 tile。

### 3. 减少 Q 侧空位，并正确屏蔽残缺页

设 $c_q$ 为 Q 块有效行数。$1\le c_q\le64$ 时用 $64\times256$ tile，$65\le c_q\le128$ 时用 $128\times128$ tile；空 Q 块跳过。两种形状面积相同，Q 较少时减少 Q 方向空算，并增大 K 方向。不同 Q 块仍保持各自的 K/V 选择集合。

残缺页中的无效 K 位置必须在 softmax 的行最大值与指数运算之前屏蔽：

$$
\widetilde S_{ij}=\begin{cases}
S_{ij},&\text{K 行 }j\text{ 有效},\\
-\infty,&\text{K 行 }j\text{ 无效}.
\end{cases}
$$

仅把 K/V 补零不够：零 key 仍可能给 softmax 分母贡献有限的指数权重。这里的“精确”是相对原有稀疏图的语义不变，并不表示恢复 dense attention，也不要求浮点逐位相同。

### 4. 反向传播重新组织任务，避免拼出错误连接

多个 Q 块会共同贡献同一份 dK、dV，因此 backward 以拼接后的 K/V tile 为单位，查找与它相关的 Q。一个 K/V owner 有八个 Page16 槽，单个逻辑 K/V 块的页不跨 owner 边界。

Q 与 K/V 都拼接后，物理上相邻不代表原来有 attention 连接。每步用一个 64-bit mask 记录八个 Q 页与八个 K/V 页之间的 $8\times8$ 连接，屏蔽原稀疏图不存在的配对。接口还支持 Q、K/V 采用不同分组，以适配独立语义聚类。方法细节见[原文 §3](https://arxiv.org/html/2610.28096v1#S3)。

## 关键发现

| 场景 | 基线与计时范围 | 论文报告的加速 |
| --- | --- | --- |
| 逻辑块全部填满 | NVIDIA BSA，裸前向 kernel | 几何平均 $1.03\times$ |
| 三维边界形成部分块的四组负载 | NVIDIA BSA，裸前向 kernel | 几何平均 $2.29\times$ |
| 五组代表性负载 | NVIDIA BSA，裸前向 kernel | 几何平均 $1.77\times$ |
| 八组 SSTA、STA、VSA 布局 | 每组最快的精确稀疏基线 | 前向 $1.13$–$4.25\times$；前向加反向 $1.02$–$2.71\times$ |
| SVG2 Wan 14B/720p trace | 最快精确稀疏基线，裸前向 kernel | $1.49\times$ |

这些结果支持的主要结论是：**原有块没有填满时，压缩有效页能明显减少执行浪费；块已经填满时，收益接近零。** 无 padding 与三维部分块两组实验的稀疏图并不相同，不能视为同一张图只切换 padding 的严格消融；各组内部 KPage 与 BSA 的前向比较使用相同稀疏图及有效行信息。

五组代表负载中的有效 Q–K 交互保持 160.6G 不变。名义物理 tile 容量由 334.1G 降至 177.5G，容量利用率由 48.1% 升至 90.5%；这是布局容量统计，不是 GPU MFU，也不是实测 BSA FLOPs。Figure 6 另计附加开销时为 180.3G、89.1%，两套统计口径不要混用。[原文 §4](https://arxiv.org/html/2610.28096v1#S4)

## 我的提问

### Q1：选中的块不是全部计算吗，为什么还会有 padding？

选中之后，块里的全部真实 token 确实都会计算。Padding 来自分块和物理摆放时的补齐，不是因为其中一部分真实 token 不重要。

例如，attention 输入的 token 网格为 $T\times H\times W=2\times10\times8$，采用 $2\times8\times8=128$ 的三维块：

| 块 | 实际覆盖区域 | 真实 token | 若补到 128 的空位 |
| --- | --- | --- | --- |
| A | 高度方向前 8 行 | $2\times8\times8=128$ | 0 |
| B | 高度方向最后 2 行 | $2\times2\times8=32$ | 96 |

选择 B 意味着完整计算这 32 个真实 token，另外 96 个只是占位。若多个被选中的块都有这种空位，KPage 才能把它们的真实部分拼起来。

### Q2：只要按三维取块，就一定有这个问题吗？

不一定。以 $4\times4\times4$ 分块为例，$8\times8\times8$ 的 token 网格能整除，每块都是 64 个真实 token；$9\times8\times8$ 的最后一层只形成 16-token 边界块，只有实现将它补到 64 时才出现对应 padding。

还要区分逻辑块大小与物理计算块大小：完整的 64-token 逻辑块若单独占据 128-token 的计算位置，仍可能空算；若两个这样的块已经拼成 128，就没有这部分空位。

判断依据应是实际 token 网格、边界处理与计算 tile，而不是“三维”这个标签。这里的尺寸是 VAE 压缩、patchify 后进入 attention 的尺寸，不是原视频分辨率或帧数。

### Q3：KPage 与 vLLM 的 PagedAttention 有什么区别？

| 比较项 | vLLM PagedAttention | KPage |
| --- | --- | --- |
| 原来的浪费 | KV cache 预留空间、内存碎片、重复存储 | 已选中物理计算块里的空位 |
| 做法 | KV 按页按需分配到不连续地址，支持共享 | 有效小页跨逻辑块拼进大计算 tile |
| 主要收益 | 同样显存容纳更多请求，提高服务吞吐 | 同样的有效 attention，少执行空位计算 |
| 重点 | KV 在显存里怎么存和寻址 | KV 加载时怎么组织计算 |

PagedAttention 同样有专用 kernel 读取不连续的页，并非只有内存分配器。它的分页本身不减少需要关注的真实 token。两者原则上可以组合，是执行设计上的推断，KPage 论文没有验证这种集成。[PagedAttention 原论文 §4–5](https://arxiv.org/html/2309.06180v1)

### Q4：一代 Sol-Attn 能借鉴吗？

Sol-Attn 用便宜的代理分数选择需要精算的块，其余块保留近似贡献。KPage 主要压缩的是被选中块的无效占位，收益条件不同。[Sol-Attn §3.2](https://arxiv.org/html/2607.24027v1#S3.SS2)

2026-10-26 查阅的公开 `sol-engine` 分支中，SM100 实现已经把两个选中的 64-token K/V 块 gather 成 128-token K/V tile，配合 64 个 Q 计算。可见 `N_MEMBER=64`、`N_PACK_HALF=128`、`_load_pack_k_half` 和 exact 配对循环。选中块为奇数时，最后一个缺少搭档的部分会被 mask。这个结论限定于该公开实现，不能泛化到所有硬件版本。[公开 SM100 源码](https://github.com/NVlabs/Sana/blob/sol-engine/techniques/sparse_backends/sol_attn/sm100/mainloop.py)

因此，不能把“细块拼成大块”都当作额外收益。若选中的块本来全满，去 padding 的空间很小；若确有大量残缺块，则可以考虑 Page16 压缩。进一步改成 16/32-token 粒度选择，再拼大 tile，是新的研究扩展，会改变选择结果、代理摘要和近似补偿，需重新验证质量与完整调用耗时。实现时也必须保证同一份贡献不会同时进入精确与近似分支。

## 局限与疑问

- **主要数字是裸 kernel 时间。** 稀疏图、页表、Q 路径分配与 backward 布局构建不计时；这些结构只有在稀疏图和块有效行数不变时才可复用。动态图需要另算构建成本，不能直接外推整模型加速。
- **部分 backward 基线语义不同。** 论文中的 NVIDIA blk128 BSA backward 不支持部分块有效长度；对应数字只是硬件计时参考。Table 2 的最快精确基线比较已排除这些 BSA backward 数字。
- **硬件信息不完整。** v1 写明单 GPU、BF16、head dimension 128 及软件版本，但未明确列出 GPU 型号，不能把引用 SVG2 结果中的 H100 当成 KPage 测试硬件。
- **SVG2 的旧 kernel 未使用匹配后端。** 该环境下其公开 VBS 路径回退 FA2，因此优先引用对最快兼容精确稀疏基线的 $1.49\times$，而非将对 VBS 的倍数当作全面领先证据。
- **创新范围需要收窄。** [FG-Attn §4.3](https://arxiv.org/html/2509.16518v1#S4.SS3) 已把零散 K/V gather 到 shared memory 大 tile。KPage 的具体贡献是保持既有块稀疏图、以 Page16 压缩块内空位，并补齐 Q 路径及精确 backward 设计。

## 我的判断

KPage 的核心价值清楚：让有效数据占满适合硬件的大计算块。它能否帮助已有 attention，实现里的块占用率比总体稀疏率更关键。

这次讨论修正了最初过宽的判断：三维分块不自动意味着 padding，选中后完整计算也不意味着物理块一定填满。评估时应同时看真实 token 数、计算 tile 容量和元数据构建耗时；在没看到具体布局与 kernel 前，不把论文的倍数套到另一套实现上。

## 下次只看这些

1. KPage 保留选中的全部真实 token，压缩的是占位空行；两个没填满的块可以共享一个大计算 tile。
2. 先查块内有效行数与物理 tile：满块几乎无收益，三维边界也只有实际补齐后才产生对应 padding。
3. 与 PagedAttention 分清内存分配和计算填充；迁移时计入页表构建、加载与近似分支的处理成本。
