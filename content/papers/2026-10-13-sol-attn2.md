## 研究问题

视频 diffusion transformer 的序列很长，dense attention 的 query–key 交互量按序列长度平方增长。稀疏 attention 只完整计算重要块，但大量小权重被同时舍弃后，会改变输出分子和 softmax 分母。Sol-Attn2 希望以便宜的压缩表示保留一部分被跳过的贡献，并让 FP8 attention 在 GB200 上实际跑得更快。

阅读依据：[Sol-Attn2 项目页](https://hp-l33-sol-attn2.static.hf.space/index.html)，页面标注 2026-10-12 research draft，2026-10-13 核对；对应公开 Space 源码快照为 `1efb6d713d4e0b723d99c89f85e9e7736f938d18`。目前正式论文、内核代码与权重链接仍标注 coming soon。网页的前端动画可读，不等于已公开计算内核。本次没有运行训练或推理复现。

相对[一代 Sol-Attn](https://arxiv.org/html/2607.24027v1)，二代延续了动态选块和近似补偿，进一步加入固定 64-token tail、FP8 前后向内核与量化感知蒸馏。ExpCast 基础思想也见于[VC-Attention §3.3](https://arxiv.org/html/2609.15810v1#S3.SS3)，不宜把每个组成部分都表述为首次提出。

## 核心方法

### 1. 先定义 attention 的输入、权重和输出

固定一个 query $q$。$k_j$ 决定位置 $j$ 与它的相关分数，$v_j$ 是该位置提供的特征向量；大写 $Q,K,V$ 是所有这些向量组成的矩阵。令 $s=1/\sqrt d$，$d$ 为 key/query 维度：

$$
a_j=s q^\top k_j,\qquad w_j=e^{a_j},\qquad
N=\sum_j w_jv_j,\qquad Z=\sum_j w_j,\qquad O=N/Z.
$$

$a_j$ 才是 QK score；$Z$ 是指数权重总和，$N$ 是 value 的未归一化加权和。$O$ 是输出向量。合并分支时合并 $N,Z$，不直接相加 Q/K/V。

### 2. 选块：完整计算哪些 KV？

视频 token 按 $4\times4\times4$ 时空立方体重排，每 64 个 token 构成一个块，attention tile 为 $64\times64$。路由器在 tile 内把 Q/K 分别池化成 8 组，计算 $8\times8$ 粗分数；据此估计 tile 的权重总量。

令 $p_{ij}^{\mathrm{proxy}}$ 是 query block $i$ 对 key block $j$ 的归一化代理权重占比，$N_B$ 为 key block 数。保留条件为：

$$
j\in E_i
\iff p_{ij}^{\mathrm{proxy}}>\frac{e^\varepsilon}{N_B}
\quad\text{或}\quad |i-j|\le1.
$$

$\varepsilon=0.47$ 在报告配置中约得到 10% block density；不同 query block 的选中集合与数量可以不同。这个阈值不保证每行都保留 10%，也不能严格推出“分布越平，保留越多”：完全均匀时，各块占比都低于正阈值，仅留下强制邻域。这里的归一化基于代理分数，不是完整原始 attention 权重。

### 3. Tail 的第一层：64 个 token 汇总成一条块记录

以下按消融表标注的已部署版本 `anchor 64 / unit 64` 解释。对未选中的块 $u$，先做普通均值：

$$
\bar k_u=\frac1{n_u}\sum_{j\in u}k_j,
\qquad
\bar v_u=\frac1{n_u}\sum_{j\in u}v_j,
\qquad n_u=64.
$$

这一步只读出并汇总向量，不计算每个原始 token 的真实 attention 权重。用该 query block 的代表 query $\bar q$ 得到一条块级权重：

$$
\alpha_u=n_u e^{s\bar q^\top\bar k_u}.
$$

块内 token 被近似为共享块均值分数；$n_u$ 保留数量贡献。因此：

$$
\widetilde N_u
=e^{s\bar q^\top\bar k_u}\sum_{j\in u}v_j
=\alpha_u\bar v_u,
\qquad \widetilde Z_u=\alpha_u.
$$

原始块内的权重通常不同，所以这一层已经是近似。页面正文写的是 8-token chunk，消融表另列 unit-8 版本；8 与 64 是压缩单元大小的不同配置，不能把两个说明混成同一实现。

### 4. Tail 的第二层：M 条块记录合并成 64 个代表 token

固定一个 query block $i$，设它有 $M_i$ 个未选中块。先产生 $M_i$ 条 $(\bar k_u,\bar v_u,n_u)$ 记录，再把这些记录划分到固定 64 个槽。每槽可以接收多个块；中间记录不是最终各自独立的 tail token。

令 $G_{i,c}$ 表示当前 query block 的槽 $c$ 接收的块集合。对非空槽，计算：

$$
S_c=\sum_{u\in G_{i,c}}\alpha_u,\qquad
k_F^c=\frac{\sum_{u\in G_{i,c}}\alpha_u\bar k_u}{S_c},\qquad
v_F^c=\frac{\sum_{u\in G_{i,c}}\alpha_u\bar v_u}{S_c}.
$$

每槽生成一个代表 key/value，并设置偏置：

$$
b_F^c=\log S_c-s\bar q^\top k_F^c.
$$

槽可以理解为累加总权重、key 加权和与 value 加权和，最终再除以总权重；多个块合并进同一份表示，所以 $M_i>64$ 不需要扩充最终 tail。固定的是输出槽数，不是每槽能代表的块数。每个 query block 单独构造自己的 tail。

**分槽函数待补充。** 项目页只给出分为 64 个槽及槽内公式，没有说明具体索引映射、是否均匀、空槽如何处理、是否根据当前未选中集合重新分组。不能把编号取模或“每槽两个块”的教学示例当成实际内核规则；前端动画的绘图映射也不足以确认内核实现。

### 5. 实际 query 读取 tail，再与保留部分合并

同一 query block 中，每个实际 query $q_r$ 分别读取 64 个代表 token：

$$
\tilde w_{r,c}
=e^{s q_r^\top k_F^c+b_F^c}
=S_c e^{s(q_r-\bar q)^\top k_F^c}.
$$

在 $q_r=\bar q$ 时，权重等于 $S_c$；其他 query 使用其自身 query 做分数修正。这里在代表 query 处保留的是先前块均值模型的总权重与加权 value，不是原始所有 token 的精确 attention。

令 $\mathcal T_i$ 为保留块集合 $E_i$ 内的全部原始 token 索引。对当前 query，保留部分与 tail 分别计算：

$$
N_s=\sum_{j\in\mathcal T_i}e^{s q_r^\top k_j}v_j,
\qquad Z_s=\sum_{j\in\mathcal T_i}e^{s q_r^\top k_j},
$$

$$
N_t=\sum_{c=0}^{63}\tilde w_{r,c}v_F^c,
\qquad Z_t=\sum_{c=0}^{63}\tilde w_{r,c},
\qquad O=\frac{N_s+N_t}{Z_s+Z_t}.
$$

“完整计算”表示展开保留块内的 token 对；FP8 运算仍有量化误差。

若先分别得到 $O_s=N_s/Z_s$ 与 $U_t=N_t/Z_t$，就按两部分总权重混合。令 $L_s=\log Z_s,L_t=\log Z_t$：

$$
L=\log(e^{L_s}+e^{L_t}),\qquad
O=e^{L_s-L}O_s+e^{L_t-L}U_t.
$$

这与 online softmax 的统计量合并相同：可以逐块更新，也可分支完成后合并。公式严格合并“保留原始 token + tail 代表 token”，不能据此说它严格恢复 dense attention；误差已经发生在前面的压缩与量化中。

### 6. 为什么没有重新算成 dense attention？

只看一个 64-query block 对 $M$ 个未选中 64-key block 的 QK 点积数：完整展开需要 $4096M$ 个点积。unit-64 tail 构造用 $M$ 个代表 query 与块均值 key 的点积；最终 64 个实际 query 读取整个 64-token tail，增加 $4096$ 个点积。这只是 tail 部分的计数示意，未包含路由的粗分数、池化、加权累加和量化开销，不能把该比例直接写成实际加速比。

最终读取 tail 的大小固定；构造 tail 仍要扫描候选块。固定稀疏比例也不意味着整个算法已经变成序列长度的线性复杂度。页面说当前 routing 与 tail construction 约占其 attention 时间的 40%，进一步融合仍在进行。

### 7. FP8、backward 与 QAD 各自解决什么？

- **FP8 + ExpCast**：QK/PV 用 E4M3 Tensor Core；从对数分数直接生成近似 FP8 权重字节，减少逐元素指数与转换开销。给指数表示留出数值范围，避免小权重过早下溢。路由与压缩公式仍可涉及指数，不能泛化成整个算法完全没有指数运算。
- **字节重放 backward**：重建 forward 实际用过的 FP8 权重，使 value 梯度使用相同权重；score 梯度走平滑的 straight-through 代理。重放字节相同与离散量化函数具有严格导数，是两件事。
- **QAD**：dense BF16 H3 是 teacher，使用 Sol-Attn2 的 student 只训练 rank-256 LoRA，在原有八个采样 timestep 匹配视频与音频预测。用 H3 自生成素材，400 步约 48 B200 GPU-hours。它适配稀疏与 FP8 误差，保留原有少步采样器。

## 关键发现

### 速度：attention、denoiser 和 request 分开读

| 测量范围 | 12 秒视频结果 | 必要条件 |
| --- | --- | --- |
| 完整 attention 调用 | 133.29 → 19.40 ms，约 6.9× | 单 GB200，BF16 Q/K/V 输入，包含量化、路由与 tail；基线为 cuDNN BF16 dense |
| 研究 pipeline 的 denoiser | 86.20 → 48.33 s，1.78× | 8-step HyperFlow，未融合研究 pipeline |
| 同一研究 pipeline 的 request | 101.76 → 63.89 s，1.59× | denoiser + VAE decode；文本编码已缓存 |
| 优化 Sol-H3 的 denoiser | 43.09 → 19.37 s，2.22× | 单 GB200，12 秒 1344×768，FastH3 4-step adapter，融合优化 |
| 同一优化引擎的完整 request | 1.89× | text encoding + denoiser + VAE decode |

引擎速度为一个 prompt 的三次 warm request 中位数；质量样例与主要 QAD 实验使用 8-step HyperFlow，不能默认为与 4-step 引擎测速是同一配置。多卡引擎的 denoiser 加速为 4 卡 2.12×、8 卡 2.09×，不是完整请求加速。

### 质量：证明更接近 teacher，不等于全面提升观感

- **免训练**：64 个 held-out prompts，同 prompt/seed，前两次 denoising 调用保持 dense；Sol-Attn2 的视频 PSNR 为 17.23 dB，top-k 为 17.04 dB，配对差值 +0.19 dB，区间 [+0.04, +0.34]。参照是 dense teacher 视频。
- **QAD 后**：32 个固定验证样本，报告的 Sol-Attn2 / top-k FP8 validation-loss ratio 为 0.963、0.974；VSA2 和 BF16 top-k exact 的比较区间包含 1，项目页明确标为 tie。
- **Tail 消融**：部署 tail 的 step-0 loss / no-tail 为 0.962 [0.924, 0.998]，支持补偿减少预测误差；更细版本相对部署版本尚未显著胜出，QAD 比较仍在进行。
- 样例支持直观比较，但尚未给出大规模人工偏好、语义/运动/音画同步评测。不能把预测 loss 或 teacher PSNR 解释成所有感知维度均更好。

免训练配置保留前两次 dense 调用；QAD 后测速让全部 denoising 调用采用 sparse，但网络内仍有六个 dense attention blocks，部分模态行也保持 dense。最高加速配置不能直接套用免训练质量结论。

## 我的提问

### Q1：100 个相同 key 为什么需要加 log 100？

这是说明 tail 数量补偿的理想例子，不是实际 block 大小。若这组 key 对固定 query 的分数都是 $a$，先从原始加权和推导：

$$
\sum_{j=1}^{n}e^av_j
=e^a\sum_{j=1}^{n}v_j
=ne^a\left(\frac1n\sum_{j=1}^{n}v_j\right).
$$

所以代表 value 可用普通均值，但代表权重必须是 $ne^a$，对应分数 $a+\log n$。$n=100$ 得到 $\log100$；一个 64-token 单元则是 $\log64$。这个例子在 tail 路径中恰好精确，不代表 tail 一般无损。

### Q2：权重不同，还能先对 v 普通平均吗？

通常不行。不同权重时，能够严格合并的是加权平均：

$$
\sum_jw_jv_j
=Z\sum_j\frac{w_j}{Z}v_j,
\qquad Z=\sum_jw_j.
$$

右侧的均值随 query 的权重改变；如果每个 query 都先准确计算它，就已经做了原来的加权工作。实际方法先用块均值做便宜近似，再在代表 query 处对块记录加权合并。不能用加权平均恒等式证明前面的普通池化无损。

### Q3：M 个未选中 block 为什么最后只有 64 个 tail token？

因为有两层汇总：每块先生成一条均值记录，多个记录再合成一个槽的代表 token。每槽可以汇总多个块，固定的是槽数；当前 query 的筛选结果与分槽规则共同决定每槽接收多少。具体分槽函数待补充。

### Q4：压缩时还读了所有 token，是否根本没有省计算？

读出 token 求均值，与为每个 query 计算每个原始 key 的点积、指数和 value 加权，是不同成本。tail 用一个代表 query 对一条块记录计算粗权重；实际 query 最后只读固定 64 个代表 token。省掉的是大量原始 token 对的交互，代价是池化与合并误差。

### Q5：两部分最后相加，是把 QKV 加起来吗？属于 online softmax 吗？

合并的是未归一化加权和 $N$ 与总权重 $Z$，不是 QKV。若两部分已分别归一化，必须按 $Z_s/(Z_s+Z_t)$ 与 $Z_t/(Z_s+Z_t)$ 混合输出。它使用 online softmax / log-sum-exp 的合并规则；可合并不等于整个路由、压缩与 attention 已完成单遍融合。

## 局限与疑问

### 博客最需要补清楚的五处

1. **把两层 tail 压缩画完整，并给出分槽定义。** 应标出原始 64-token block → 块均值记录 → 64 槽 → 64 代表 token，以及每个 query block 单独构造 tail。补充映射、空槽、动态未选中集合如何处理；统一正文 unit-8 与部署表 unit-64。否则读者无法判断 $M>64$ 如何处理。
2. **从标准 attention 顺序推导数量偏置和共同归一化。** 先定义 score、$N/Z$、value 普通均值与加权均值，再说明 $\log n$、anchor 与逐行修正。明确 anchor 处匹配的是池化后的模型、其他 query 为近似；用一个不同 key 的小例子标出误差发生在哪一步。
3. **说明便宜在哪里，以及当前究竟如何执行。** 补一张计算量与时间分解图，区分均值/路由、槽内汇总、FP8 selected core、tail core、最终合并。标明哪些已融合、哪些仍单独执行；“读出 tail 固定一块”不代表构造成本恒定。
4. **把 tail、FP8 backward、QAD 串成同一个目标。** 先说稀疏与 FP8 分别引入什么误差，再说 tail 与 QAD 分别修复什么，最后解释为何训练需要重放 forward 字节。把“exact replay”和 score 的 STE 分开，避免把代理梯度说成量化函数的严格导数；用小表说明与 Sol-Attn1 / VC-Attention 的继承和新增部分。
5. **统一首页结论与实验配置，并限定质量结论。** 首页 2.2× 应注明 denoiser；完整 request 为 1.89×。集中列出免训练/QAD、8-step/4-step、dense warm-up、密度与精度。质量图应让读者看出 tail 与 QAD 各自带来多少改善，并明确 teacher fidelity、统计持平与感知质量的区别。

当前 best-validated router 为 two-pass；真正 single-pass routing + compression 尚在规划。新 FP8 core 当前处理 selected blocks，tail 仍使用之前的 core，进一步融合进行中。FastH3、VDN-H3 的跨模型/runtime 表比较的是系统速度，不能当成同一路由下的 attention 单项排名。

## 我的判断

本次阅读后，最值得保留的思路是：用带质量偏置的压缩表示补回 sparse attention 跳过的贡献，同时保留可合并的 softmax 统计量。核心公式的合并关系清楚；实际是否得到好的速度与质量取舍，仍取决于块内池化、分槽、代表 query、FP8 内核与 QAD 的共同作用。

当前公开结果支持 H3 / GB200 特定配置下的加速与 teacher 误差改善，尚不足以宣称普遍无损。复现前优先等分槽函数、空槽处理、完整可执行内核与对应 adapter/config 公布；不要自行把教学示例补成官方实现。
